## The fuzzy_link nominal error 5.502e-15 versus the archive 5.615e-15

The question: why does the re-evaluation of `r02-F2-001` give `5.5020494742180965e-15` while the archive holds `5.614918919956449e-15`, already on HEAD?

Facts (numbers in `results/tester/008-b4.json`):
1. It is not a code change. Source trees at `3f51ef0` (the commit that created the entry), `5fe990f` (before B1/B2), `8e1dce6` (HEAD at start) and the working tree all give `5.5020494742180965e-15` on this machine. The alternate-angle errors (`3.4388927549462143e-15`, `5.913696799282053e-15`) are bit-identical to the archive in all of them.
2. Provenance of the entry (round-002.json): git `6d221d5` (dirty), numpy 2.5.4, scipy 1.18.1 (same as now), platform `Linux-5.15.0-139-generic ... glibc2.31`, 48 CPUs (the former desktop). Today: Linux 7.2.15, glibc 2.44, 20 CPUs, i7-12700KF. The fuzzy_ub entry `r12-F1-012` was created on this machine and is bit-identical.
3. Other `fuzzy_link` archive entries show the same effect: of the four valid entries two differ from the archive at the 1e-16 level (`r00-seed-010`: `3.2455e-15` vs `3.1464e-15`; `r02-F2-001`), two are bit-identical (`r00-seed-000`, `r01-F1-001`). All differences are below $2.2\cdot10^{-16}$ absolute, i.e. one unit of machine epsilon, on a quantity whose floor is about $3\cdot10^{-15}$.
4. I tried to reproduce the archive value by forcing other OpenBLAS kernels (`OPENBLAS_CORETYPE`): Haswell and Zen give `5.502e-15` (as default), Sandybridge `5.522e-15`, Nehalem `4.606e-15`, Prescott `4.608e-15`; none gives `5.615e-15`, and those that differ also change the alternate values, which the archive does not. So the kernel alone does not explain it.

Conclusion: the difference is roundoff-level and independent of the code under test (not introduced by B4, B3, B2 or B1). Guess: the BLAS/LAPACK or glibc libm build on the old 48-core desktop (or a different thread count for that run) produced a different last-digit rounding in the nominal pass only; I could not pin it exactly. Does it matter: no. The archive key (the sort key is built from counts: `[12, 644, 1183, 4]`) is unchanged, validity has margin $\sim10^{4}$ against the tolerance $10^{-10}$, and `M10_G1` checks `op_norm_error <= 1e-10` and the key, not the digits. It would matter only for a test that demanded bit equality of the error with the archive (none exists; the Phase C replay will rewrite these numbers anyway).
