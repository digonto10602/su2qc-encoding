Aer reduction (sound version). The liveness of an ancilla is decided per input code by my sparse engine with the relative-phase Toffoli `rccx` kept as one monomial 3-qubit gate (its Hadamard-based decomposition makes every target look live). A gate touching a never-non-zero qubit is replaced by $\langle 0_D|G|0_D\rangle$ on its live qubits: identity (dropped), or a diagonal gate (e.g. a phase from `rz`/`crx` on a $|0\rangle$ target, kept as a `DiagonalGate`); zero diagonal entries (control patterns that never occur on that input) are set to 1; anything else raises. This fixes a weakness of report 217 (dead gates were just dropped). The final comparison against the dense target would expose a wrong reduction.

### 3.9 The 62-qubit limit (spec peak 80)

Yes, a hard limit exists.
- Source: `src/su2plaq/evaluate/sparse_sim.py:298-299`, `run_batch`: `if n > 62: raise ValueError("at most 62 qubits")`, with `n = qc.num_qubits`. It is inherited from the laptop evaluator; the rishon evaluator reaches it via `rishon/verify.py` -> `evaluate/evaluator.py:315` (`_simulate` -> `ss.run_batch`); also `verify._code_block` (line 78), `frames._simulate_frame`, `results.outer_electric_check` call `run_batch`. Reason: basis states are `int64` keys (`sparse_sim.py:300, 316`), so bits $0..62$ are usable; the guard 62 is slightly conservative (63 qubits would fit, 64 cannot); `_coalesce` (line 57) packs `col<<n | key` only while $n+\lceil\log_2 n_{\rm cols}\rceil\le62$ and otherwise uses `lexsort`.
- The count is the total `qc.num_qubits` including the 32 idle outer qubits $o[16..47]$, so the circuits can have at most $62-48=14$ ancillas. The spec's cap of 80 (`peak_qubit_cap()` $=16+32+32$, tested by `test_M6_K1`/`K3`) therefore cannot be reached.
- Measured on the valid F5 circuit padded with $k$ extra ancillas (compute and uncompute `CX(0,q)` so they are live, or left idle):

| total qubits | `run_batch` | `evaluate_circuit` / `run_candidate` | forced `engine='aer_mps'` |
|---|---|---|---|
| 59, 60, 62 (also `run_candidate --trial`) | ok | valid, ok | at 62: `ok=False`, `reason='leak'`, error $1.6$ to $2.6\times10^{-9}$, `certified=False` |
| 63 | `ValueError: at most 62 qubits` | uncaught `ValueError` (traceback, not a verdict) | same as 62, not certified |
| 64, 65, 77 | same | same | `CircuitTooWideForTarget` (Aer maximum 63) |
| 80 | same | same | same |
| 81 | - | `invalid: max_qubits` (`81 qubits > cap 80`), a proper verdict | - |

- So no valid circuit with 63-80 qubits can be evaluated: the sparse engine refuses, and the `aer_mps` fallback is only entered after `SimCapExceeded` (`evaluator.py:312-318`), never after this `ValueError`. Even when forced it gives accuracy $\sim10^{-9}$ at 62-63 qubits, above the $10^{-10}$ tolerance, `certified=False`, so it can never produce `valid`.
- Consequence for the loop: `run_round` calls `E.evaluate_program` without a `try` around the `ValueError` (`rishon/compress/round.py`, the proposal loop), so one proposer program with $\ge63$ qubits aborts `round --evaluate` for the whole round before any file is written. `run_candidate` shows a traceback. F2 and F4 sit exactly at 62.
- The restriction is not physical: my engine compacts the used qubits. The F5 circuit padded to 80 qubits (29 live pad ancillas, 48 used qubits) is exact on my engine, block error $3.15\times10^{-14}$, leak 0 (`tester-218-qubitcap-mine.json`), at 63, 64 and 80 qubits alike. A compaction of the touched qubits in `run_batch`, or a catch of the `ValueError` into a reason, would make the cap of 80 meaningful. This is a planner or builder matter (shared laptop file, not edited by me).
