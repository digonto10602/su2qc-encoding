## Observations (no failure)

- O1: **file mode change**. `tempfile.mkstemp` creates the file with mode `0600`, so a `robust.json` or `summary.json` written by the new helper is `-rw-------`, where the old `write_text` gave `-rw-r--r--` (checked: the written copy has mode 0600, the committed file in the tree 0644). Git tracks only the executable bit, so no diff, and the same user reads it; it matters only if another account or a cluster job reads these files. A `os.chmod(tmp, 0o666 & ~umask)` before the `os.replace` would keep the old mode (guess at the cheapest fix; not required).
- O2: **a failed refresh shrinks the cache**. The `finally` block writes the store that holds only the entries finished so far, so a failure in the middle of a `refresh=True` run replaces a complete old cache (6 entries in my toy) by the finished ones (3). Nothing is corrupted and the next run recomputes the rest; without `refresh` the reusable old records are put into the store as they are reached, so only the entries after the failure point are lost. It matches the code comment ("the finished entries are kept for the next run"), but it is a cost, not a gain, when the old cache was complete.
- O3: the OOM kill of the M9_C1 worker is a resource accident of running four workers beside the other agents' jobs, as in report 428; the test passes alone (3 passed, 370 s). The `-n 4` sweep still reaches about 2 GB per m9 worker.
- O4: `write_headline_step` writes its output file with a plain `write_text` (not atomic). It is a single-writer file and no test races on it; mentioned only for symmetry with the robust.py fix.
- O5: `results/fuzzy/compressed_step_headline.json` carries `git_dirty: true` and commit `284bd40`; the coordinator regenerates it on a clean commit (already planned). The numbers in it do not depend on this (check 4a to 4d).
